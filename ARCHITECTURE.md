# Architecture

RedAnts is an Umbraco 17 / .NET 10 application combining a public marketing website with a self-service ticketing system, backed by **Azure SQL in every environment** (dev and prod).

## Solution layout

The solution `RedAnts-WebApp/RedAnts.slnx` contains a shared kernel, three module projects and one test project per project, plus the architecture and browser tests:

- **`RedAnts-WebApp/src/RedAnts.Kernel`** — the shared kernel: `SwissTime`, `DomainException`, `ValidationException`, `ConcurrencyException`, `CheckResult`, `EmailAddress`, `Money`. Plain class library without package references; every module and the Host reference it.
- **`RedAnts-WebApp/src/RedAnts.Host`** — the web app (`AssemblyName=RedAnts`, so publish output and deployment stay unchanged). Hosts `Program.cs`, Umbraco, `Infrastructure/Shared/`, the Website slice, `uSync/`, the Umbraco template views and shared wwwroot assets. References the two class libraries; consumes ticketing only through `AddTicketing(...)` / `UseTicketing*()` extension methods.
- **`RedAnts-WebApp/src/RedAnts.Ticketing`** — Razor class library (namespaces `RedAnts.Ticketing.*`) with build-time-compiled views for the whole ticketing slice, cut into capability folders under `Features/` that each hold their slices, ports, Blazor components, MVC views (the `/scan` page included) and adapters, plus the ticketing static assets under `/_content/RedAnts.Ticketing/`.
- **`RedAnts-WebApp/src/RedAnts.Show`** — Razor class library (namespaces `RedAnts.Show.*`) for the soundboard (`/show`, backoffice section "Show", SQL schema `show` on `ConnectionStrings:showDbDSN` with fallback to the Umbraco DSN, `Show:Storage` options for a separate blob container) with the capabilities `Board`, `Admin`, `Remote` and `Sounds`.

Umbraco composers in the class libraries are discovered through Umbraco's assembly scan of referenced Umbraco-referencing assemblies (the same mechanism uSync relies on). The Umbraco template views (`TicketingHome`, `TicketEvent`, `TicketSeason`, `TicketVenue`, `SaisonsPromo`) must stay physical in the Host's `Views/` folder: Umbraco templates are DB entities backed by content-root files that the seeders read from disk and the backoffice edits. The class libraries suppress the Umbraco JSON schema copy and exclude their raw `.cshtml` from publish, both of which would otherwise collide with the Host's files (NETSDK1152).

## Layering (ports and adapters)

Within each project, three layers with dependencies pointing inward (`Infrastructure` → `Features` → `Domain`):

### `Domain/`
Pure business model: entities, enums, value objects, and the exceptions from the Kernel (`DomainException` for broken aggregate rules, `ValidationException` with the field name for bad input). No dependency on Umbraco, ASP.NET, or any framework; aggregates change state through named methods such as `EventPrice.WithSalesQuota(...)` that copy every other field unchanged. Examples: `Domain/` (`Event`, `Season`, `Venue`, `BillingAddress`, `PostalCode`), `Domain/Admission/` (`Admission`, `AdmissionEvaluator`, `FreeEntry`, `Occupancy`) and `Domain/Sales/` (`Order`, `EventTicket`, `SeasonSingleTicket`, `SeasonPass`, `MemberCard`, `EventVisit`/`EventVisitLog`/`EventFreeEntry`, the pricing aggregates `EventPrice`/`SeasonPrice`/`CategoryPrice`, and the enums in `SalesEnums.cs`).

### `Features/`
Application layer, cut vertically by capability instead of by technical kind. Every folder under `Features/` is one capability (Ticketing: `Admin` (the backoffice shell and its shared widgets only), `Admission`, `Catalog`, `Checkout`, `Email`, `EventBundles`, `FlexTickets`, `Helpers`, `MemberCards`, `Newsletter`, `Orders`, `Public`, `SeasonPasses`, `Stats`, `Tickets`; Show: `Board`, `Admin`, `Remote`, `Sounds`) and always has the same shape:

- The root holds the slices, one file each with a static outer class, a nested `Command`/`Query` record and a nested sealed `Handler` (registered through `TicketingFeatures.Handlers` / `ShowFeatures.Handlers`, checked by the architecture tests), the plain step classes that several handlers share (`CapacityReservation`, `OrderFulfillment`, `TicketScanning`), the ports (`I….cs`, one interface per file, next to the slices that use them) and the controllers and Razor components of the capability.
- `Admin/` holds the Blazor components, dialogs, report DTOs and import/export controllers of the capability; `Views/` holds its MVC views; `Infrastructure/` holds its adapters.
- `Features/Shared/` holds what several capabilities render with (`MoneyFormat`, `EmailLayout`, `MailMarkdown`, `Views/_TicketsLayout.cshtml`).

Controllers, components and handlers depend only on ports, never on concrete infrastructure. Handlers never call other handlers.

### `Infrastructure/`
Adapters that implement the ports and integrate with Umbraco and external services. An adapter lives in the `Infrastructure/` folder of the capability whose port it implements (namespace `RedAnts.Ticketing.Features.<Capability>.Infrastructure`): NPoco records and repositories, the report readers, the mailers, the Payrexx gateway, the Turnstile verifier, the QR/PDF renderers and the Umbraco catalog readers. Adapters of one capability may use the records of another capability's `Infrastructure` namespace. The top-level `Infrastructure/` keeps only what belongs to the module as a whole: `TicketingComposer`, the `AddTicketing`/`UseTicketing*` extensions, `FeatureViewLocationExpander`, the additive migration chain `TicketingMigration`, `SessionCacheSchema`, `TicketingMappers` and `Content/` (code-first seeders, `TicketingAliases`, price defaults). The Show module keeps its repositories, schema and Spotify client in its top-level `Infrastructure/` while that folder stays small. The Host has `Infrastructure/Shared/` (backoffice auth, themes, `DomainErrorFilter`) and `Infrastructure/Website/` (the public website content types and seeding).

## Content slices

Independent slices share the Umbraco instance and must stay decoupled (Show adds a third, content-free slice as its own project):

1. **Ticketing**: events, seasons, event tickets / season single tickets / season passes / member cards, ticket bundles, season add-ons, a guest shopping cart, per-season price tiers and per-event/season pricing with quotas, admission scanning, PDF/QR ticket delivery, and a purchase flow with Payrexx payment and a Microsoft Graph confirmation email queued through a SQL outbox.
2. **Website**: the public marketing site. A `flexPage` document type holds a `content` Block List of element types (`heroElement`, `headerElement`, `eventListElement`), rendered through `Views/FlexPage.cshtml`, `Views/Shared/_SiteLayout.cshtml`, and `Views/Partials/Blocks/{alias}.cshtml`.

Website code must not reach into ticketing internals. If a real dependency arises, route it through a port. The event-list block is the sanctioned bridge: it reads ticketing seasons through the published-content API, not through ticketing internals.

## Ticketing data model

The catalog (Season, Venue, Event) is Umbraco Document Types. Everything transactional is NPoco tables, built by `CreateTicketingSchema` in `RedAnts-WebApp/src/RedAnts.Ticketing/Infrastructure/TicketingMigration.cs`. The build is fully idempotent and re-runs on every boot: `TicketingMigrationComponent` resets the recorded migration state before each run, and every table is created only when missing (`EnsureTable`/`TableExists`) while additive columns are gated by `ColumnExists`. A new table or column therefore appears on the next start with no database drop, and the "recorded state says applied but the table is gone" desync (which happened when a dev database was swapped between parallel sessions) cannot occur. See `README.md` for the full entity-relationship diagram and enum value tables.

Design rules:

- **Enums are persisted as their integer value.** `Category` (`TicketCategory`, or `MemberCategory` on `MembershipCards`), `Status` (`OrderStatus`/`TicketStatus`), `PaymentMethod`, the order's `PaymentSource`, `BillingType`/`BuyerType`, `TicketType`, `FreeEntryType`, the visit-log `Type` (`VisitLogType`), `OrderItemKind`, `AddOnScope`, and the outbox `Status` (`EmailStatus`) are all `int` columns. Records store `(int)theEnum`; repositories cast back, and raw SQL in the admin report readers compares against `(int)` casts. There is no category master table and no `CategoryCode`/`CategoryName` — the display label comes from `TicketCategory.DisplayName()`. Full enum value tables live in `README.md`.
- **No enforced foreign keys.** Tables reference each other (and the Umbraco catalog) by id only; `EventId`/`SeasonId` hold the Umbraco content node id. This keeps the ticketing tables decoupled from the content tree and from each other.
- **Pricing (`EventPrices`/`SeasonPrices`) is 0..1 per event/season** (unique on the node id), each with n category sub-rows (`Category`, `SalePrice`, `Quota?`). `EventPrices` additionally carries the event-level `TotalSalesQuota` (Verkaufskontingent gesamt) and `AdmissionQuota` (Einlasskontingent, persons). `EventPricingReader` marks a category sold out once its `Quota` or the event's `TotalSalesQuota` is reached by the valid issued `EventTickets`.
- **Admissions are one `TicketEventVisits` row per `(event, ticket)`.** There is no `CheckedOutAt`; the individual in/out scans are appended to `TicketEventVisitsLogs`, and `IsInside` is the visit's current presence. Free-entry persons (players, staff, officials, Swiss Unihockey free cards) are admitted spontaneously with `TicketType = FreeEntry` (`TicketUuid` null) and their kind recorded in `TicketEventFreeEntries` (`FreeEntryType`).
- `EventTicket` and `SeasonSingleTicket` carry a `bool Redeemed` (the single-admission tickets); `SeasonPass` and `MemberCard` are multi-event and have no redemption flag. `Orders` is the immutable financial record; tickets link to it by optional `OrderId`.

On boot `PriceTierSeeder` idempotently seeds each season's default price tiers (Erwachsen / Jugend / Kind plus a Sonderaktion tier) and backfills the additive `TierId` on existing rows; `EventPriceDefaults` (an `INotificationAsyncHandler<ContentSavedNotification>`) gives a newly created event its price set from the season defaults. `MemberCardOrderCleanup` and `OrderItemsBackfill` are one-off idempotent startup reconcilers (decouple member cards from orders; backfill `OrderItems` for pre-existing orders).

## Code-first content types

Content types are defined and maintained in code, not by hand in the backoffice. Each slice follows the same pattern:

1. A `IComposer` registers an `INotificationAsyncHandler<UmbracoApplicationStartedNotification>`.
2. On application start the handler ensures document types, element types, and data types (e.g. the Block List) exist, then seeds sample content.
3. Every step is **idempotent** (check-then-create / reconcile), so it runs safely on every boot and on an existing database.
4. All type and property aliases live in one `*Aliases` static class per slice (`TicketingAliases`, `WebsiteAliases`). Never scatter alias string literals through the code.

Reference implementations: `RedAnts-WebApp/src/RedAnts.Ticketing/Infrastructure/Content/TicketingContentTypeSeeder.cs`, `RedAnts-WebApp/src/RedAnts.Host/Infrastructure/Website/WebsiteContentTypeSeeder.cs`.

### Block List value format (Umbraco v17)

Block List content values are JSON with `contentData` (array of `{contentTypeKey, key, values:[{alias,culture,segment,value}]}`), optional `settingsData`, an `expose` array (`{contentKey,culture,segment}`), and `layout["Umbraco.BlockList"]` (array of `{contentKey,contentUdi,settingsKey,settingsUdi}`). The website seeder builds this JSON directly when creating sample pages.

## Reading content (ModelsBuilder = Nothing)

`Umbraco.CMS.ModelsBuilder.ModelsMode` is set to **`Nothing`** in `appsettings.json`. There are no generated typed models. Read all content untyped:

```csharp
var title = page.Value<string>(WebsiteAliases.HeroTitle);
var media = page.Value<MediaWithCrops>(WebsiteAliases.HeroImage);
```

Do not introduce or assume ModelsBuilder-generated classes.

## Razor compilation is split

- **Host views** are runtime-compiled (`RazorCompileOnBuild`/`RazorCompileOnPublish` are `false`, needed for the backoffice). `dotnet build` does not surface view errors there; validate by running the app and requesting the page. Known trap: naming a `foreach` variable `page` breaks compilation, because `@page.Url()` is parsed as the `@page` Razor directive. Use another name such as `item`.
- **Ticketing and Show views** in the class libraries compile at build time; view errors fail `dotnet build`. They live in `Features/<Capability>/Views/` and are resolved by `FeatureViewLocationExpander` from the controller's namespace (see "Feature folders and view resolution" below). The runtime view engine falls back to the precompiled application parts for view paths that have no physical file in the Host, so explicit `~/Features/...` paths from Host views (`TicketVenue.cshtml` uses `~/Features/Shared/Views/_TicketsLayout.cshtml`) keep working.

## Routing and URLs

- Ticketing links use fixed MVC routes (for example `/tickets/event/{sqid}`), where `{sqid}` is a Sqids-encoded id. They do not depend on Umbraco content-node URLs, so reordering root nodes is safe. Public/admin routes are English (`/cart`, `/checkout`, `/seasons`, `/scan`, `/admin/members`, `/admin/season-passes`, `/admin/event-tickets`, `/admin/flex-tickets`); the seasons folder content node is renamed to "Seasons" so it serves at `/seasons`.
- The public homepage is the first `flexPage` at the content root. The website seeder sorts it to the first root position so it serves at `/`, which demotes the ticketing content node's URL harmlessly (ticketing uses the fixed routes above).

## Adaptive navigation

`Views/Shared/_SiteLayout.cshtml` renders a shared nav. When a page opens with a hero or header block, `ViewBag.TransparentNav = true` makes the fixed bar float transparent over the image with white text; a scroll handler switches it to a solid white background with black text past 60px. Pages without a leading hero/header get a solid nav from the start.

## Infrastructure and boot

- **Database**: **Azure SQL in every environment** (dev and prod). `appsettings.json` sets provider `Microsoft.Data.SqlClient` with an empty DSN; the real connection string is injected as the App Service app setting `ConnectionStrings__umbracoDbDSN` (prod) or via user secrets pointing at the shared dev database (local). The SQL Server provider ships transitively with `Umbraco.Cms`. There is no SQLite bootstrap anymore (the earlier SQLite + WAL setup was removed when dev and prod were unified on Azure SQL). `BackgroundServiceExceptionBehavior.Ignore` is set so a transient Azure SQL timeout inside a hosted background service cannot crash the whole app.
- **Session / cart state is server-side in SQL**: `AddDistributedSqlServerCache` backs `AddSession` with the `AppSessionCache` table (created idempotently by `SessionCacheSchema.Ensure` on the same `umbracoDbDSN`). The guest cart (`SessionCartService`) is JSON under the session key `RedAnts.Cart`; only the session id rides in the `RedAnts.Cart` cookie. This survives app restarts and scale-out (previously the in-memory session lost every cart on a redeploy/recycle).
- **Outbound email is an outbox**: `IEmailSender` enqueues into the `OutboxEmails` table (`OutboxEnqueuer`); a hosted `OutboxDispatcher` background service drains it, sending through Microsoft Graph (`GraphEmailTransport`, `Graph:*` config) with retry/backoff and a retention purge. Nothing sends synchronously on the request thread, so a slow mail API never blocks checkout.
- **Deployment**: GitHub Actions (`.github/workflows/deploy.yml`) build/publish/ZipDeploy to Azure App Services in resource group `RG_RedAnts`. A push to a `feature/**` branch deploys **DEV only** (`app-redants-dev`); a push to `main` deploys **DEV and then PROD** (`app-redants-prod`, gated to `main`). The pipeline also sets per-environment app settings (Payrexx instance/secret, SMTP/Graph, Imaging HMAC, `Orders__NumberPrefix`, runtime mode) and warms up `/`. One-time provisioning script and details in `deploy/README.md` and `RedAnts-WebApp/deploy/azure-setup.sh`.
- **Culture**: default thread culture is `de-CH`, set on `DefaultThreadCurrentCulture`/`UICulture` at the top of `Program.cs`. This is deliberately global, not display-only: Blazor `@bind`, implicit `ToString()`, and number/date parsing all follow `de-CH` (dd.MM.yyyy, apostrophe thousands separator). **Do not reach for `UseRequestLocalization` to localize display strings**: Umbraco's request pipeline overrides the request culture with the content language of the install (English by default), so a negotiated `Accept-Language` culture never survives to view rendering on content pages — that is exactly why weekday names once rendered in English for German visitors. Localized display (currently the weekday on the event page) instead formats explicitly with `DisplayCulture.From(Request)` (`Features/Public/DisplayCulture.cs`), which reads the browser's top `Accept-Language`: English browsers get English day names, everything else gets `de-CH`. Date/number layout stays Swiss everywhere.
- **Development**: OpenIddict transport security is disabled in Development so the backoffice works over HTTP; unattended install/upgrade is enabled.
- **External services**: Payrexx (payment), Microsoft Graph (transactional email, `Graph:*` client-credentials, sender `tickets@redants.ch`), Turnstile (captcha), and Azure Blob Storage (prod media) are configured via `appsettings` / user secrets. Secrets are never hardcoded; Development uses Cloudflare test Turnstile keys and empty Payrexx credentials.

## Design rationale and gotchas

The codebase carries no inline comments (the code is meant to speak for itself). The non-obvious "why" behind certain constructs, the kind a future developer would otherwise rediscover the hard way, is recorded here instead.

### Persistence and schema migration
- **Provider-aware ALTER TABLE.** Umbraco's `Alter.Table` / `Delete.Column` builders throw `NotSupportedException` on SQLite, which once aborted the whole migration. The migration therefore detects the provider (`Database.DatabaseType.GetType().Name.Contains("SQLite")`) and runs raw `Execute.Sql("ALTER TABLE ...")` on SQLite while using the Umbraco builder elsewhere. Now that every environment runs on Azure SQL the SQLite branch is dead, but any future additive column change should keep following the same guarded pattern (see `AddFlexTicketBundles`, `AdjustMemberCardColumns`).
- **Member cards have no `Price` column** by design (only season passes are priced); the legacy column was dropped.
- **Timestamps are `datetimeoffset` with the Swiss offset.** Azure runs in UTC, the club's admins read the database directly, and a bare `datetime` cannot say which clock it belongs to; every persisted instant in the Ticketing slice (`CreatedAt`, `PaidAt`, `OccurredAt`, `SignedUpAt`, `TransferredAt`, `NextAttemptAt`, `SentAt`) is therefore a `datetimeoffset(7)` column that carries the Europe/Zurich offset of the moment it was written, so the stored wall clock is what happened in Winterthur while the instant stays DST-safe and comparable. The write rule is `SwissTime.Timestamp` (never `DateTime.UtcNow` or `DateTime.Now`), the C# type is `DateTimeOffset`, and the display rule is `SwissTime.ToSwiss(...)` in views, PDFs, mails and CSV exports (never `.DateTime`, `.LocalDateTime`, `.UtcDateTime` or `ToLocalTime()`, which would depend on the machine's zone). The migration step `timestamps-datetimeoffset` converts per column: drop the indexes that include it and its default constraint, `ALTER COLUMN ... datetimeoffset(7)` (the old UTC values become `+00:00`), `UPDATE ... AT TIME ZONE 'W. Europe Standard Time'` (keeps the instant, switches to the Swiss offset with the right DST), then recreate the indexes with the same name, columns and uniqueness; a fresh database gets the type straight from `Create.Table<T>()`. Consequence for reports: `CAST(x AS date)` and `DATEFROMPARTS(YEAR(x), ...)` in SQL now group by the Swiss day, which is the intended behaviour (`VisitorStatsReader` takes Swiss `DateOnly` bounds and converts them with `SwissTime.StartOfDay`). What stays `datetime`: birthdays (a date), and the sales windows `AvailableUntil`, `PassAvailableFrom`, `PassAvailableUntil`, `TicketAvailableUntil` (Swiss wall-clock deadlines), plus the Umbraco tables, `AppSessionCache` and the Show schema.

- **Multi-table writes run in one unit of work.** `IUnitOfWork` (`Features/Checkout/IUnitOfWork.cs`) takes a block of writes as a delegate; its adapter `ScopedUnitOfWork` opens one ambient Umbraco core scope (`ICoreScopeProvider.CreateCoreScope()`), so every repository call inside joins that scope's database and transaction, and a throw leaves the scope uncompleted and rolls the whole block back. Inside the scope: the draft order plus its journal entry (`PlaceOrder`), the mark-paid plus the tickets, passes, billing copy and order add-ons (`OrderFulfillment`), the order plus its items and both journal entries (`CreateAdminOrder`), the refund row plus the order status, the accounting journal entry and the ticket deactivation (`RefundOrder`), and each of the four card and ticket imports as a whole. Outside on purpose: the Payrexx gateway and refund calls (no transaction stays open while an external service answers), the capacity counters (optimistic `Version` updates whose retry would otherwise doom the scope; they are released as a compensation after the commit), the confirmation mail and the add-on notification, the newsletter opt-in, and the best-effort `OrderItems` write of the online fulfilment, which stays swallowed and covered by `OrderItemsBackfill` instead of rolling a paid order back. Two Umbraco scope properties drive that split: a nested scope created with `autoComplete: true` completes even when an exception unwinds, so a swallowed exception inside the block would commit the part written before it, and a nested scope disposed without `Complete()` dooms its parent silently, which is why `ScopedUnitOfWork` throws a `DomainException` when `Complete()` returns false instead of reporting a write that never happened.

### Blazor Server backoffice
- **`UmbracoEventStatusEditor` wraps `IContentService.Save`/`Publish` in `Task.Run` on purpose.** Those APIs are sync-over-async; invoked directly on a Blazor Server circuit's `SynchronizationContext` they deadlock (the UI hangs with no exception). `Task.Run` moves them off that context while still propagating exceptions. Do not "simplify" it away.
- **Umbraco readers wrap reads in `EnsureUmbracoContext()`** because they are also called from the Blazor admin over SignalR, which has no request-scoped Umbraco context. The call is nest-safe, so the MVC path is unaffected.
- **`TicketingAdminState` is per-circuit shared state.** Blazor Server scopes it to the SignalR connection, so every admin tab shares one instance for the session. Contract: on init a tab uses `SelectedSeasonId` when set and still valid, otherwise falls back to the current season and writes that back; on dropdown change it writes back. A fresh circuit (app reload) starts null, so the first tab shown re-establishes the current-season default. It also carries `SelectedEventId`/`SelectedBundleId` and raises `Changed` on any set so `TicketingAdminComponent` can mirror the position into the URL.
- **Admin position lives in the URL query.** `TicketingAdminComponent` parses `tab`/`season`/`event`/`bundle` on init (seeding `TicketingAdminState` before any child mounts) and rewrites them via `NavigateTo(replace: true)` whenever the tab or state changes, so a copied link reopens the same tab, season and event/bundle. URL writes are gated behind the first `OnAfterRender`: the host renders the component with `render-mode="Server"` (no router), so navigating during non-interactive init would throw and there is no `LocationChanged` re-render loop to worry about afterwards. `event`/`bundle` are only emitted on the tabs that own them; the shared state keeps the last value so detouring through another tab and back restores it.
- **Narrow inline write-ports.** `IEventStatusPublisher` and `ISeasonStatusPublisher` are kept separate from the read-only catalog ports (`IEventReader`, `ISeasonReader`, `IVenueReader`) so the catalog read contract is not widened; setting status republishes the node so the published cache and all catalog readers reflect it. Admin report readers query the Sales tables directly through `IScopeProvider` rather than reusing ticket repositories, to stay decoupled from in-flight repository and port changes.
- **Admin modals close on `@onmousedown`, not click,** so releasing a text selection outside the modal does not dismiss it.
- **Inline editors auto-focus on open and close on blur.** `InlineEditBase` focuses the editor element on the first render after `BeginEdit` (via `EditorElement`), which is what lets a click-away raise `blur` at all; `HandleBlur` then abandons the edit exactly like ESC. The blur handler is guarded against `ConfirmOpen`/`Busy` because opening the confirm dialog (or clicking its buttons) blurs the editor, and an unguarded close would dismiss the pending save. `@onchange` fires before `@onblur`, so a changed value has already raised the confirm dialog by the time blur is handled.

### Ticket QR tokens and scanning
- Tokens are compact HMAC-signed strings (`RA1.<payload>.<sig>`), **signed but not encrypted**: the fields are readable because the scanner must read them, and the signature (a truncated 128-bit HMAC-SHA256) makes them unforgeable without the server secret. `Create` and `TryVerify` must truncate identically for the `FixedTimeEquals` compare. Production must set `Tickets:QrSecret`; dev falls back to a key derived from the Umbraco global id so tokens survive restarts (logged as a warning).
- `ScopeId` is the `EventId` for single-admission tickets and the `SeasonId` for passes and member cards. The QR encodes the **absolute** `/ticket/{token}` URL so a generic phone camera opens the web ticket, while the door scanner takes the last path segment as the token.
- `IQrCodeRenderer` uses QRCoder's managed encoders (no `System.Drawing`) so it runs on the Linux App Service; ECC level Q is a deliberate glare/wear versus size tradeoff.
- Admission model: a first scan checks a person in, a re-scan checks them out (so a ticket becomes free again on exit). Ticketed admissions are never blocked by the hall quota (the quota is informational and only gates anonymous free walk-up entries). A `SeasonSingle` flexticket binds to the first event it is admitted at (`RedeemedEventId`) and only that event admits it thereafter.
- **The 8-character manual code is kept unique across all four ticket tables at allocation time.** The door scanner's manual fallback resolves the first 8 hex of a ticket's `Uuid` with `WHERE Uuid LIKE '<code>%'` across `EventTickets`, `SeasonSingleTickets`, `SeasonPasses` and `MembershipCards`, taking the first match. A shared prefix (birthday collision on the 32-bit prefix, or the same prefix in two tables) would make manual entry ambiguous. `TicketCode.AllocateAsync` therefore counts existing rows with the same prefix across all four tables before each insert and draws a fresh `Guid` on the astronomically-rare hit; every ticket-creating insert path routes its `Uuid` through it. The check is case-insensitive both ways (input lowercased, stored `Uuid` lowercased, SQL collation `_CI_`), so a helper may type the code in any case. It is a best-effort guard, not a constraint: a per-table unique index enforces full-`Uuid` uniqueness, but no single DB constraint can span the four tables, so a simultaneous double-insert of the same prefix is theoretically possible and simply left to the vanishing odds.
- **Helper-to-scan attribution is by name, not id.** Each visit-log row stores `ScannedBy`, a free-text operator name; a logged-in helper writes their `Helper.FullName` (see `HelperNameAsync` in `Program.cs`). The helper admin's per-helper scan overview therefore matches `HelperScanRow.Person == Helper.FullName` rather than a foreign key, and check-ins (`Type = 0`) versus check-outs (`Type = 1`) are summed separately. Two helpers with an identical full name would merge, and a manually typed operator name that happens to equal a helper's name would be attributed to that helper; both are accepted tradeoffs of the name-based logging.
- **Helper login passwords are pre-declined adjective+noun word lists, not runtime-inflected.** `HelperPassword` holds six literal arrays: nouns split into `Masculine`/`Feminine`/`Neuter` and the adjective in all three genders (`-er`/`-e`/`-es`, indeclinable ones like `Lila`/`Rosa` unchanged). `Generate` picks a noun and takes the matching-gender adjective form, so every password is grammatically correct by construction with no declension logic to get wrong. The lists were curated (nice, concrete, everyday words), the gender taken from an authoritative German noun dataset rather than guessed, umlauts transliterated to `ae/oe/ue/ss` so passwords stay ASCII-typable, and words filtered out that are sensitive/insulting, very long, or unusual. To extend or regenerate, edit the arrays directly.

### Content seeding
- **`EnsureLabel` matches the data type by Name, not `EditorAlias`.** Several built-in `Umbraco.Label` types exist; an alias match grabs "Label (pixels)" and renders a string link as "px". The Name lookup plus explicit `umbracoDataValueType = "STRING"` avoids that.
- The website seeder runs after the ticketing seeder (`[ComposeAfter]`) so the sample homepage's event-list block can reference an existing season. Template aliases are prefixed (e.g. `TicketEvent`) so they do not collide with the MVC purchase views through Umbraco's root view-location expander.
- Access-link fields are computed from the published Umbraco URL (empty until first publish, filled on the next save); writes happen only on an actual change to avoid an infinite `ContentSaved` re-trigger loop.
- `EventAdmissionReportReader` counts asymmetrically on purpose: card visits use `COUNT(DISTINCT TicketUuid)`, while FreeEntry admissions carry no ticket uuid and use `COUNT(*)`. Do not unify these.
- **The venue picker's `startNodeId` config is a bare document Key (GUID), not a UDI.** In the new backoffice the Document Picker UI (`Umb.PropertyEditorUi.DocumentPicker`) reads the `startNodeId` config value and passes it straight through as the tree root's `unique`, which is a plain GUID. Storing the folder UDI (`umb://document/...`) there resolves to no node, so the venue tree comes up empty and the event's "Ort" appears unchangeable. `EnsureVenuePicker` therefore writes `venuesFolder.Key.ToString()`; the idempotent update path migrates any old UDI value on the next boot. The server-side `ContentPickerConfiguration` only exposes `ignoreUserStartNodes` in v17, so the start-node restriction is a purely client-config concern.

### Purchase, orders, exports
- **Checkout goes through Payrexx.** The cart is first persisted as a `Draft` order carrying a JSON `FulfillmentPayload` snapshot, then a Payrexx gateway is opened (`IPayrexxGateway`, HMAC-SHA256 signed request and webhook). Fulfillment — issuing one ticket per unit, marking the order `Paid`, sending the confirmation mail, honouring the newsletter opt-in — runs exactly once and idempotently, driven by the Payrexx **webhook** (`/payrexx/webhook`) and re-checked when the buyer returns to `/checkout/success?t=<token>` (the order id wrapped in a DataProtection token, so the success page is IDOR-safe). A refund is a real Payrexx refund (`RefundGatewayAsync`) for online-paid orders and a manual status change otherwise; a gratis-only order skips the gateway entirely. VAT is 0 by design because Swiss sports entry fees are exempt (Art. 21 Abs. 2 Ziff. 15 MWSTG); the model stays VAT-ready for the day the club becomes liable.
- **Email never sends on the request thread.** `IEmailSender` (`OutboxEnqueuer`) writes the message into the `OutboxEmails` table; the hosted `OutboxDispatcher` drains it through Microsoft Graph (`GraphEmailTransport`) with retry/backoff and a retention purge, so a slow or failing mail API cannot block or fail a checkout. Order, member-card, season-pass and helper-invite mails all go through it; subject/body come from an editable Umbraco `MailTexts` node via `ITicketingMailSettings`.
- **Orders carry `OrderItems` and a `PaymentSource`.** Every sale (online and every admin-created order via `IAdminOrderFactory`) writes financial line items to `OrderItems`; `PaymentSource` records how a manually created order was paid (Cash/TwintCode/Terminal/Invoice for priced orders, Sponsoring/Marketing/Goodwill for gratis ones), while online checkout sets it to `Online` automatically. Member cards are part of membership, not a sale: they carry no price and create no order.
- `CartController.Add` always resolves price and name server-side and never trusts a posted price, and distinguishes a fetch call from a full post via the `X-Requested-With: fetch` header (progressive enhancement: without JS the same form posts normally and the server redirects).
- **`PaymentMethod` name clash:** the type exists in both `Domain.Ticketing` and `Domain.Ticketing.Sales`. The Sales one is authoritative and kept as an aliased `using` in `OrderRepository`; removing or reordering that alias reintroduces an ambiguous-reference compile error.
- **Season add-on scope (`SeasonAddOn.Scope`):** each add-on is either `PerPass` (charged once per season pass, so its cost multiplies with the pass line quantity, e.g. a physical card, opt-in and off by default) or `PerOrder` (charged once per whole order regardless of how many passes, e.g. a Livestream subscription). `PerOrder` add-ons live in a separate `Cart.OrderAddOns` collection (not on the pass line) and are deduplicated by id, which is what enforces "max one per order" even though the public season page still offers the checkbox on every category card. In the fulfillment snapshot both scopes flow through `FulfillmentSnapshot.AddOns`, but `PerOrder` entries are written with quantity 1 so `FulfillAsync` (webhook-deferred) stays scope-agnostic. The additive `Scope` column defaults to 0 (`PerPass`), so add-ons that existed before this change keep the old per-pass behaviour until an admin sets the scope.
- **Money and mail addresses are value objects, not raw decimals and strings.** `Money` and `EmailAddress` from `RedAnts.Kernel` carry the sales amounts (`Order.SubtotalNet`, `VatAmount`, `TotalGross`, `OrderItem.UnitPrice`, `OrderRefund.Amount`, `CartLine.UnitPrice`, `CartAddOn.Price`, `Cart.TotalAmount`, `CategoryPrice.SalePrice`, `SeasonCategoryPrice.PassPrice` and `TicketPrice`, `SeasonAddOn.Price`) and the addresses (`BillingAddress.Email`, `Helper.Email`, `NewsletterSignup.Email` plus the optional `MemberCard.Email`, `SeasonPass.Email`, `CardHolder.Email`). NPoco records, read models and the session cart JSON stay on primitives, and the mapping is explicit at the adapter boundary: `FromPersistence` wraps with `Money.Stored` or `EmailAddress.TryCreate`, the repositories write `.Amount` and `.Value`, so loading a row never rewrites what is stored. Three factories keep the rounding intentions apart. `Money.Chf(x)` snaps a price a person enters to the five-rappen grid (Swiss cash rounding) and is used where a price enters the system (`CategoryPrice.Create`, `SeasonCategoryPrice.Create`, `SeasonAddOn.Create`, the admin ticket and season-pass dialogs). `Money.Of(x)` keeps rappen precision (two decimals, away from zero) for amounts that are derived rather than typed: order totals, the VAT split, refunds and the cart lines fed from the catalog, which are already on the grid. `Money.Stored(x)` keeps the database decimal untouched. Adding or comparing two currencies throws a `DomainException`. The five-rappen rule was only introduced after checking the agent database: all 39 event prices, 13 season prices, 3 add-on prices, 70 order totals, 90 order item prices and 8 refund amounts are multiples of 0.05 with at most two decimals, so no stored row changes meaning.
- **A format check belongs to the value object, and `ValidationException` is a `DomainException`.** `EmailAddress.Create` (a strict ASCII pattern: plus addressing accepted, umlauts in the local part rejected), `EmailAddress.Optional` for the fields a card may leave empty, and `Birthdate.Validate` replaced the hand-rolled checks in `CheckoutController`, `TicketImportCsv`, `MemberContactRules` and the member card dialogs. `ValidationException` derives from `DomainException` and carries the field name, so `DomainErrorFilter` renders it as a `ValidationProblemDetails` for the APIs and as a redirect message otherwise, while the `catch (DomainException)` that the Blazor dialogs and the checkout controller already had shows the message without a second code path. The CSV import is the one place that does not fail on a bad address: it warns per row and drops the value, because one broken cell must not stop a whole bundle import.
- **Serienbrief export (`FlexBundleExportController`):** RTF keeps this dependency-free (Word opens it natively). Each QR is embedded as a PNG in an RTF `\pict\pngblip` group; the intrinsic pixel size is read from the PNG IHDR (big-endian width/height at bytes 16 to 19 / 20 to 23), converted to himetric (0.01 mm) at 96 dpi for `picw`/`pich`, while `picwgoal`/`pichgoal = 2551` twips renders about 4.5 cm square. CSV exports prepend a UTF-8 BOM so Excel picks the right encoding; `MemberCsv` defaults to `;` (Swiss Excel) and also writes a BOM for umlauts.

### Checkout workflow and capacity reservations

- **Capacity is reserved when the order is placed, not when it is paid.** `PlaceOrder` turns the cart into an `OrderSnapshot`, and `CapacityReservation` asks `EventPrice.Reserve` / `SeasonPrice.ReservePasses` for every event and season in it. Those aggregate methods hold the rule (total sales quota, per-tier quota, sale window; conversions count towards the total but not towards a tier) and bump `Reserved` counters on the price row and its category rows. The repositories persist that with a conditional `UPDATE ... WHERE Version = @v`; a lost race throws `ConcurrencyException`, the step reloads and retries once and then denies with `CapacityDenied.Contended`. Remaining capacity everywhere is `quota - sold - reserved`; `sold` stays a count over valid tickets because a stored counter would drift with admin issues, imports and cancellations.
- **Reservations are released exactly once.** Fulfilment (`OrderFulfillment`) releases them right after its unit of work committed the paid order and the issued tickets, because those tickets now count as sold; `CancelDraftOrder`, the Payrexx cancel path and the `DraftOrderExpiry` hosted service (drafts between two days and 30 minutes old; older drafts are abandoned checkouts from before the reservations existed and stay untouched) release them after `TryCancelDraftAsync` succeeded. Both transitions are conditional updates, so a webhook and the success page cannot double-release. Drafts created before the reservation columns existed release nothing because the counters floor at zero.
- **The cart is a domain aggregate stored in the session.** `SessionCartRepository` keeps the historic JSON property names so carts that were open during the deploy survive; quantity caps, conversion caps and orphaned order add-ons are rules of `Cart`, not of the controller.
- **A rule that needs I/O is a `Check` slice, and the command shares its domain method.** `CanCheckout`, `CanRefund` and `CanConvert` answer `CheckResult.Allowed` or `Denied(reason)`, where the reason records (`CheckoutDenied`, `RefundDenied`, `ConversionDenied`) carry the German sentence the UI shows, so a wording change happens in one place. The rule itself lives in the aggregate: `Cart.CheckoutBlocker(CheckoutContext)` (empty cart, a full hall, a conversion-only event, express eligibility), `Cart.ConversionBlocker(...)` (event contingent and per-card cap) and `Order.RefundBlocker(remaining, amount, viaPayrexx, payrexxEnabled)` (paid status, open rest, amount, Payrexx). The facts those methods need come from a step, not from the check: `CheckoutEligibility` asks the occupancy reader and the conversion rules once and hands the result to the cart, and `PlaceOrder` calls the same step, because a handler never calls another handler. The commands keep their guard (`PlaceOrder`, `RefundOrder` and `AddConversionToCart` deny with the same reason) so a stale page cannot get past them; the UI asks the check first to disable the pay button on `/checkout` and `/checkout/express`, to show the reason instead of the refund form in `RefundOverlay`, and to answer the convert form on the event page with the reason or the tier choice.

### Admission workflow

- **Scan rules are a domain service, state is an aggregate.** `AdmissionEvaluator.Evaluate(ScanContext)` decides test, reject or admit from facts only (ticket record, scope, status, season, flex redemption, conversion rule, inside count and cap); `Admission` holds the visit rows and check-in/check-out logs of one ticket at one event and enforces the cap itself (member cards get one visit row per admission, every other ticket reuses its single row). `TicketScanning` is the step both `ScanTicket` and `ScanCode` share: read facts, load the admission, evaluate, mutate, save, mark the ticket redeemed, answer with the occupancy taken after the write. Free entries have their own aggregate and `FreeEntryQuota.Allows` (hall full blocks SU free cards and children, quotas count fixed contingents).

### Catalog workflow

- **Umbraco is the master for catalog content.** Event names, dates and times and season names and periods are edited in the Umbraco content tree only; the admin tables show them as plain text (the earlier inline editors wrote through `IContentService` behind the editor's back and were removed). Sales status stays editable in the admin because it is an operational switch, not content.
- **Quotas and prices change only through the aggregates.** The `Catalog` slices load `EventPrice`/`SeasonPrice`, call `With…` and save; `EventPrice` refuses a sales quota above the admission quota (`SalesAboveAdmission`), which can surface on existing events whose quotas already contradict each other: raise the admission quota first. Deleting a price tier that already sold cards is rejected by `SetSeasonPricing` before anything is written; `FreeEntryQuota.Create` rejects negative contingents.

- **Read models per screen (Phase B, public sales path).** The Umbraco templates, the checkout controllers, the web ticket page and the catalog admin tabs inject query handlers only. Each query returns an immutable record shaped for its screen (`TicketingHome`, `EventForSale`, `SeasonForSale`, `SeasonPassOffers`, `NextEvent`, `CartSummary`, `WebTicket`, `EventForAdmin`, `SeasonForAdmin`, `SeasonTierPrice`) through a reader in the capability's `Infrastructure/` that composes the published content, the pricing and the admission counts, while the write side keeps only `I<Aggregate>Repository` with load, save, delete and the conditional reservation save. The catalog content (`Event`, `Season`, `Venue`) has no write side in ticketing, so `IEventReader`, `ISeasonReader` and `IVenueReader` are the lookups that handlers and adapters use. A screen with several dialogs is one reader with one method per dialog (`ISeasonsForAdminReader` serves the seasons tab, its pricing and add-on dialogs and the season pickers), and the Catalog capability is cut into the sub-features `Shop/` (the sale queries) and `Pricing/` (the pricing commands and queries) to keep the root at the ports and the admin slices.

### Order workflow

- **Order state changes are aggregate methods, not editor code.** `Order.ChangeStatus` applies the admin transitions (paid, draft, cancelled, refunded) with the existing guards and reports whether anything changed; `DeactivatesTickets` tells the slice when to block the tickets of the order. Refunds go through `RefundOrder`: the order must be refundable (`RequireRefundable`), the amount must stay within the remaining rest reported by the refund summary, and a Payrexx refund is only attempted for orders that were paid through Payrexx (`PaidThroughPayrexx`); a failed gateway call marks the pending refund as failed instead of leaving it open. `CreateAdminOrder` replaces the order factory for backoffice sales.

### Card workflow

- **Every write to a card, pass, ticket, bundle or helper is a slice.** The four card admin pages used to call repository ports directly from their dialogs; the capabilities `Tickets`, `SeasonPasses`, `MemberCards`, `FlexTickets`, `EventBundles` and `Helpers` hold one thin slice per action (38 of them, sorted by the aggregate they change) so the pages only build commands and render results. The rules that used to sit in the components or in the deleted editor adapters moved into the aggregates: `MemberCard.Edit`, `FlexTicketBundle.Rename` (blank and length checks, uniqueness checked by the slice through the port) and the event ticket rule that a ticket that is not valid can never count as redeemed.

### Naming after the slice migration

- **The legacy name list is empty for Ticketing.** Every remaining `…Service`, `…Adapter`, `…Editor` and `…Store` in the ticketing module was renamed after what it does (`IEventStatusPublisher`, `UmbracoEmailBridge`, `ConvertibleCardResolver`, `EventBundleTicketsReader`, `TicketTokenSigner`, `TicketPrinting`, `PasswordGenerator` in the domain, `PersonFields` for the Blazor person form). `legacy-names.txt` only tolerates what the Show module still carries until its own rebuild; the naming test fails for any new type with such a suffix.
- **Host and Website need no slices.** The website is read-only content (FlexPage and blocks), its seeders are Umbraco notification handlers, and the Host only wires modules together; the architecture tests guard that the Host never reaches into ticketing internals.

### Show module

- **Show reads and writes through NPoco like everything else.** The raw `SqlClient` stores were replaced by `ShowProfileRepository` and `ShowSettingsRepository`; `ShowDatabase` hands out Umbraco's scoped NPoco database unless `ConnectionStrings:showDbDSN` names a separate server, in which case it opens an NPoco database on that string. Profiles are still stored as one JSON document per profile (the board and the Companion module consume that shape), so the domain model keeps its JSON property names and `ShowProfileRules` validates ids and names before a save. The pages and controllers depend on the ports and slices of the capabilities `Board`, `Admin`, `Remote` and `Sounds` only; the architecture rules apply to the Show module like to Ticketing.
- **The board owns what the Streamdeck shows.** Profile, open folder and playback state live only in the board's Blazor circuit, so the board publishes its 15 grid cells after every render (`PublishBoardView`, withdrawn on dispose) into the in-memory `IShowBoardViews` singleton, and the Companion module mirrors them as slots 1–15 instead of baking tile ids into buttons. `GET /api/show/view?since=<version>` long-polls for 25 s so a folder or profile change reaches the Streamdeck at once without hammering the App Service; `GET /api/show/press/{slot}` lets the board resolve the slot against what it currently shows, which keeps the Streamdeck and the touch screen consistent. The view is per instance and not persisted: with more than one App Service instance the board and Companion would have to hit the same one (the App Service runs one instance).
- **Rooms are learned from Companion, not configured.** Every `/api/show` request that carries a `room` records it through `RecordShowRoom`; `ShowRooms` keeps the names as a JSON list in the existing `show.Settings` row `Show:Rooms` (no schema change) and the last-seen time only in memory, so the board can offer the rooms in a picker and mark live ones. The board remembers its choice in `localStorage` (`?room=` wins); deleting a room in the admin only removes the name, and the next Companion request with it records it again.

### Member card categories

- **Block 4 Firma is a category, not an address property.** `MemberCategory.Company` (stored as 2) replaces the earlier guess "Block 4 card with a company address"; the migration step `member-card-company-category` moved those cards once. Mail defaults follow the category (`MemberCardMailKinds`), and the bulk sender groups cards by bundle and category so one editable text goes to one homogeneous batch ("Bundle – Kategorie"), which is what the club actually mails.

### Access gates
- **Site access gate.** When `BasicAuth:Password` is set, a middleware fronts the public site with a soft pre-launch lockdown (not real security). An unauthenticated visitor is redirected to a `/__gate` password form; the correct password — also accepted as `?key=<password>` appended to any URL — sets the `RedAnts.Gate` cookie. A curated `IsExempt` allow-list lets through everything that must always work: the backoffice and its Blazor hub/framework (`/umbraco`, `/admin/ticketing`, `/_blazor`, `/_framework`, `/App_Plugins`), the Payrexx return and webhook (`/checkout/success`, `/checkout/cancel`, `/checkout/status`, `/payrexx/webhook`), the ticket pages (`/ticket`), the footer legal pages, `/warmup`, and static assets. **Adding a new public route means adding it to `IsExempt`, or the gate blocks it.**
- **The scanner has its own gate, independent of the site gate.** `/scan` is exempt from the Basic gate but guarded by a helper login: an operator authenticates at `/scan/login` (or via a `/scan/<code>` deep link) against the `scanHelper` Umbraco members, which sets a separate `RedAnts.Helper` session cookie (`RedAnts.HelperSession.v1` DataProtection). This lets helpers unlock the scan surface without ever getting the site-gate password. Host-based landing routes the roots in `Program.cs`: `scan.`/`scan-dev.`→`/scan`, `admin.`/`admin-dev.`→`/umbraco`, everything else→`/ticketing/`.
- **Admin controllers carry real backoffice authorization.** The custom admin dashboard and every CSV export/import controller (`TicketingAdminController`, `MemberExportController`, `SeasonPassExportController`, `EventBundleExportController`, `FlexBundleExportController`, …) are decorated with `[Authorize(AuthenticationSchemes = Constants.Security.BackOfficeAuthenticationType)]`, so member PII and valid admission tokens are gated by Umbraco backoffice auth, not merely by the pre-launch Basic gate. The backoffice authenticates with a Bearer token that never matches a Basic header, which is why those paths are on the gate's exempt list rather than behind it.
- **Backoffice login is Microsoft-only (Entra ID), existing users only.** `BackOfficeAuthComposer` (`Infrastructure/Shared/`) registers an OpenID Connect provider via `AddBackOfficeExternalLogins` when `BackOfficeAuth:TenantId/ClientId/ClientSecret` are set, with `DenyLocalLogin = true` (no password form). It links **only pre-existing** Umbraco users by e-mail: auto-create is blocked by throwing inside `OnAutoLinking` when `!user.HasIdentity` (that callback runs before `CreateAsync` in `BackOfficeSignInManager`, so no orphan user is persisted, whereas returning `false` from `OnExternalLogin` would only block sign-in after creation). `OnExternalLogin` is the per-login gate that rejects any non-`@redants.ch` identity. **Leaving the three settings empty keeps the classic Umbraco login as break-glass.** Because the app runs behind the App Service reverse proxy, `UseForwardedHeaders` (X-Forwarded-Proto/Host) is enabled so the OIDC `redirect_uri` is built as `https://…` and matches the registered redirect URIs. The three admin hosts (`admin`, `admin-dev`, `localhost`) must each be registered as `/umbraco-entra-signin` redirect URIs (`RedAnts-WebApp/docs/backoffice-entra-appreg.ps1`).

### Front-end
- **One ticket look across four surfaces (online ticket, checkout confirmation, e-mail, PDF).** The design is a credit-card (ISO ID-1) portrait card, monochrome Red Ants red (`#D02D38`, `#B0242E` for the small red date); the ticket type is read from the kicker + title only (`TicketDisplay.Kicker`/`TypeLabel`), no per-type colour or emblem. The two Razor surfaces share `Features/Tickets/Views/Partials/_TicketCard.cshtml` + `wwwroot/css/ticket-card.css` (`rtk-*`, driven by `TicketCardModel`); the card height is **content-driven on screen** (a fixed `aspect-ratio` + `overflow:hidden` clips on mobile) and only forced to exact 54×85.6 mm in `@media print`. The e-mail rebuilds the same card as inline-styled tables (no SVG/notches) and the PDF rebuilds it in QuestPDF on a real 54×85.6 mm page. The abriss notches use a `--rtk-notch` variable set to the surrounding background per host. `ConfirmationTicket` carries `Type` + `DateText` (resolved in `CheckoutController.FulfillAsync` via `IEvents`/`ISeasons`) so the confirmation card shows the same fields as the others.
- **The custom 404 page is served by a response-buffering middleware, not `UseStatusCodePagesWithReExecute`.** Umbraco writes its own "nonodes" body for unmatched content routes, which starts the response and makes the re-execute middleware a no-op. The middleware in `Program.cs` therefore swaps `Response.Body` for a `MemoryStream` on extension-less page GETs (skipping `/umbraco`, `/App_Plugins`, `/_blazor`, `/_framework`, `/api`, `/ticket`, `/warmup`); if the final status is 404 it discards the buffered body and writes the static `wwwroot/404.html` (branded, fully static, so no view engine or content node is needed), otherwise it copies the buffer through unchanged.
- **Security headers are set in one middleware via `Response.OnStarting`** (so they apply to redirects and short-circuits too). `X-Content-Type-Options`, `Referrer-Policy` and (over HTTPS) `Strict-Transport-Security` are global; the `Server` header is removed via Kestrel `AddServerHeader=false`. `X-Frame-Options: SAMEORIGIN` is set everywhere except `/next/embed` (which needs cross-site framing and sets its own `frame-ancestors *`). A conservative `Content-Security-Policy` is applied only to public front-end responses and skips the backoffice, Blazor, scanner and embed paths, because those need inline/eval and their own framing rules; the policy keeps `'unsafe-inline'` for scripts and styles because the public views rely on inline styles and handlers throughout.
- **`RuntimeMode` is `Production` in base config, overridden to `BackofficeDevelopment` in `appsettings.Development.json`.** Umbraco's production-mode validators require `Global:UseHttps=true` (set in base, `false` in dev), `WebRouting:UmbracoApplicationUrl` (set), `ModelsBuilder:ModelsMode=Nothing` (set) and a Release build (CI publishes Release). Runtime Razor compilation stays enabled: the `RazorRuntimeCompilationValidator` only fails for `ModelsMode=InMemoryAuto`, which is not used here.
- **`/warmup` server-side preloads the core runtime-compiled views** (`/`, `/ticketing/`, `/seasons/`, `/next`, `/next/embed`, `/umbraco`, and the first public season detail) by looping HTTP requests back to its own host, carrying the site-gate cookie when the gate is active so the real views compile rather than the gate page. The deploy warmup step calls `/warmup` after the app answers.
- **The warm-up walks the pages one after another, not in parallel.** A cold Umbraco boot rebuilds the published cache while the runtime-compiled Host views compile on a shared lock, so a parallel batch makes every content route queue behind the same work and all of them blow the same client deadline together; the output then shows timeouts for `/`, `/ticketing/` and the season pages although the site answers in milliseconds seconds later. `WarmupController` requests the pages sequentially with a 45 second page timeout, one retry per page when a timeout hits, and a 100 second total budget after which the remaining pages report `not reached`, so the response still fits the pipeline step's own limit.
- **The scanner is warmed with a minted helper session and renders without prerendering.** `/scan` only answers for a valid `RedAnts.Helper` cookie, so the deploy warmup never reached it and the first helper after each deploy waited for the cold Blazor circuit, the scanning readers and their JIT (minutes on the B1 plan, sometimes a client-side 499). `WarmupController` now mints the cookie for the first active helper of a public season with the shared `HelperSessionCookie` constants, requests `/scan` with it and calls the venue and upcoming-event readers the scanner uses. `Features/Admission/Views/ScanTickets.cshtml` (served by `ScanController` at `/scan`, the scan middleware fills the helper session it renders) mounts `TicketScanner` with `render-mode="Server"` instead of `ServerPrerendered`: the page answers immediately with the shell and the component runs once the circuit is up, so a slow first render can no longer time out the HTTP request; prerendering brought nothing for a logged-in single-purpose app.
- **`/next/embed` is a standalone slim widget for cross-site iframe embedding** (the club's main page). It renders `NextEventEmbed.cshtml` with `Layout = null` (no site nav/footer, self-contained styles) showing the next public event's title, home-vs-opponent logos and a "Hier Tickets kaufen" link that navigates the top window (`target="_top"`) to the event's absolute purchase URL. The action sends `Content-Security-Policy: frame-ancestors *` so it can be framed anywhere; this is deliberate and safe because the widget is public, read-only and carries no forms or session data. `/next` (without `/embed`) still redirects to that same next event.
- **The scanner service worker (`scanner-sw.js`) exists solely to make the app installable** (browsers require a registered service worker with a fetch handler); it does no offline caching because the scanner needs a live Blazor Server circuit, so its `fetch` handler is a deliberate network passthrough.
- `wwwroot/css/ticketing-admin.css` is the single source of truth for all five admin tabs (identical row/header heights, dropdown width via `--ta-field-w`, toolbar, sortable headers, edit-icon column, overlay). Keeping every rule there rather than in per-component `<style>` blocks is what keeps the tabs visually identical.
- **Editable-value convention:** an inline-editable cell renders the `InlineEditBase` `.ta-inline` button, which now carries a persistent dashed underline (muted, turns accent on hover); a plain fixed cell has none. This is the shared visual cue "this value can be clicked to edit" — reuse `.ta-inline` (via the `Inline*Edit` components) for editable values and leave read-only values as plain text so the two are always told apart.
- **Season tiers and their promotions (Sonderaktion):** a promotion is a second `PriceTier` whose `PromoOfTierId` points at the base tier (its `SeasonCategoryPrice` row carries the action price/quota/until). The season pricing modal shows each promo as a tinted sub-row under its tier, toggled per tier with the `.ta-promo-toggle` pill, so any tier — including custom ones — can get an action. On save, `SaveEdit` renumbers the kept tiers' `SortOrder` to their list index before persisting, so the edited rows and the re-fetched tiers (both ordered by `SortOrder`) pair up positionally without ambiguity even for freshly added tiers.
- The web ticket gives each ticket type its own header accent colour (`wt-head--{spiel|flex|saison|member|free}`) so a stack of tickets is told apart at a glance; the type name still appears as text, so colour is a redundant cue, not the sole signal.
- **Ticket delivery (PDF):** every ticket is downloadable at `/ticket/{token}/pdf` (QuestPDF, Community licence set once at startup in `TicketDeliveryComposer`; the QR is the same signed ticket-page URL). QuestPDF relies on `SkiaSharp.NativeAssets.Linux.NoDependencies` and its embedded default font, so it renders on Azure App Service Linux without extra system packages.
- Team logos (home team / opponent) render inside a fixed `.team-logo` box (`wwwroot/css/site.css`, `object-fit: contain`) shared by the ticketing home, the season page, the event page and the `eventListElement` block. Without a fixed width, a wide/panoramic club logo at a fixed height stretched the row and distorted the layout, so the box constrains both dimensions and letterboxes each logo to a uniform size.
- The event page embeds the venue map and the "Route öffnen" directions link from the venue's `googleGeoId`, which is treated as a Google **Place ID**: the classic keyless embed uses `q=place_id:<id>` and the directions link uses the official Maps URL scheme `?api=1&destination=<name>&destination_place_id=<id>`. When a venue has no geo id, both fall back to the `"<name>, Winterthur"` text query so a map still renders.
- Footer legal links (Impressum, Datenschutzerklärung, AGB) are content-driven: they are `legalPage` nodes grouped under a single `footerFolder` root node ("Footer"), and `_SiteLayout` renders one link per published child ordered by sort order, so adding a node under Footer adds a footer link with no code change. `LegalPageContentFinder` resolves the clean single-segment URL (`/impressum`, `/agb`, …) by matching the node's `slug` regardless of where the node sits, so the pages keep root-level URLs even though they live under the folder. The startup seeder creates the folder, moves any pre-existing root-level legal pages under it and republishes them (Umbraco's `Move` drops the published state), then seeds an AGB placeholder. Scanner and Verwaltung stay hard-coded in a separate, de-emphasised footer row because they are internal routes, not content. Caveat: while the pre-launch gate is active, a new footer slug must also be added to `IsExempt` in `Program.cs` or the gate blocks it.

### Entra access, deploy-time migrations and the agent test track

- **No SQL passwords and no storage keys.** Azure SQL and Blob Storage authenticate three identities through Entra: the App Service managed identity (`db_datareader`, `db_datawriter`, `UPDATE` on the three sequences, no DDL), the GitHub OIDC deploy principal `redants-github-deploy` (additionally `db_ddladmin`), and the developer's `@redants.ch` account (Entra administrator of `sql-redants-ch`). `RedAnts-WebApp/docs/setup-entra-access.ps1` creates the users and role assignments idempotently. Gotcha: `az sql server ad-admin create` takes the tenant of the CLI's default context, which is not the Red Ants tenant on the developer machine; the script therefore sets the administrator through an ARM `PUT` with the explicit `tenantId`.
- **Schema changes run before the deploy, never in the web app.** `dotnet RedAnts.dll --migrate` adds `Migrations:RunNow=true` to configuration, boots Umbraco (unattended upgrade included), lets `TicketingMigrationComponent` and `ShowMigrationComponent` run and returns before Kestrel starts. The pipeline runs it on the runner with `Authentication=Active Directory Default` (the `azure/login` context) when the environment variable `SQL_DSN` is set. `Migrations:RunAtBoot` defaults to `true`; the pipeline writes `Migrations__RunAtBoot=false` together with the passwordless `APP_DSN`, so only an environment that already runs on the managed identity skips boot-time migrations, while an environment still on a SQL login keeps migrating at boot until it is switched. `TicketingMigrationComponent` no longer resets the stored plan state on every boot; Umbraco's `Upgrader` skips a plan whose stored state equals the final step, and `Migrations:ForceToken` replays it once per distinct token value (the token is remembered in `umbracoKeyValue`).
- **Local runs never migrate the shared dev database.** `appsettings.Development.json` sets `Migrations:RunAtBoot=false`; only the Agent launch profile (against `sqldb-redants-agent`) and the pipeline migrate step turn it on. Umbraco stores the plan state in `umbracoKeyValue` (`Umbraco.Core.Upgrader.State+Ticketing`) and refuses to run a plan from a state it does not know, so one session booting a branch with an unmerged step against the dev DSN moved the dev state past main and every deploy to dev (any branch, and therefore prod, which depends on it) aborted in the migrate step until the key was reset by hand. Test new steps with the Agent profile or by deploying the branch.
- **Blob clients from account URLs.** `Umbraco:Storage:AzureBlob:Media:AccountUrl` and `Show:Storage:AccountUrl` replace the connection strings. The media provider (`Umbraco.StorageProviders.AzureBlob` 17.1) parses `ConnectionString` as a URI when `TryCreateBlobContainerClientUsingUri` is configured, so `Program.cs` copies the account URL into `ConnectionString` and supplies a `BlobContainerClient` built with `DefaultAzureCredential`. `DefaultAzureCredential` is referenced through the `AzureId` extern alias in Host and Show because `Azure.Core` 1.55 and `Azure.Identity` 1.14 both declare the type.
- **Session-isolated `az login`.** All agent-driven Azure access uses `AZURE_CONFIG_DIR` inside the session scratchpad with a device-code login for the Red Ants tenant. With only `--tenant` given, the developer's global az context resolves to a guest identity without rights, so the isolated login is required for `Active Directory Default` to carry the member account.
- **Agent test track.** `sqldb-redants-agent` is a Basic copy of the dev database (separate schemas were rejected: Umbraco and NPoco use unqualified table names resolved through the login's default schema, and `dbo.AppSessionCache` plus `show.*` are hard-wired). The `Agent` launch profile runs on port 5606 against it with the classic backoffice login and `Email:Transports=None`, which keeps every mail in `OutboxEmails` (the dispatcher reschedules messages that have no transport). `RedAnts-WebApp/tests/RedAnts.BrowserTests` drives Chromium through Playwright for .NET and skips unless `E2E_BASE_URL` is set; the folder name avoids the `.gitignore` rule `*.e2e`, which matches `RedAnts.E2E` on case-insensitive Windows checkouts.
- **`_framework/blazor.server.js` needs `RequiresAspNetWebAssets`.** Since .NET 10 the Blazor Server script ships in the SDK pack `Microsoft.AspNetCore.App.Internal.Assets`, and the Web SDK only pulls that pack into a project that contains `.razor` files of its own. The Host has none (all components live in the Ticketing and Show class libraries), so without `<RequiresAspNetWebAssets>true</RequiresAspNetWebAssets>` in `RedAnts.Host.csproj` the script is neither served locally nor published; the App Services kept working only because a copy from an earlier publish (July 2026) survived the zip deploys. The `.webmanifest` content type is registered through `Configure<StaticFileOptions>` so `UseStaticFiles()` keeps the options that the framework post-configures.
- **SQL logins and storage keys are switched off.** `sql-redants-ch` runs with Entra-only authentication (the former logins `redants_app`, `redants_backup` and `redantsadmin` no longer work; the matching Key Vault secrets are historical), and both storage accounts have `allowSharedKeyAccess=false`, so account keys and SAS tokens are rejected. Anonymous read is off as well (`allowBlobPublicAccess=false`, every container `off`): nothing in the accounts is reachable without an Entra identity. Every `az storage` call therefore needs `--auth-mode login`. Backups no longer come from `az sql db export` (it needs a SQL login): Azure SQL keeps 14 days of point-in-time restore plus long-term retention (weekly 8 weeks, monthly 12 months, yearly 5 years, set by `.github/workflows/backup.yml`, which also reports the restorable backups every Sunday). Restore with `az sql db restore --time …` or `az sql db ltr-backup restore`.

- **No blob is public; both surfaces stream through the app.** Umbraco media was already served by the app: the Azure provider registers an `IFileProviderFactory`, so Umbraco's media file provider reads the container with the managed identity and the pages emit relative `/media/...` URLs. The soundboard was the only real dependency on anonymous read, because `Show:Storage:PublicBaseUrl` pointed the browser straight at `https://stredants<env>.blob.core.windows.net/show`. That option is gone. Sounds now come from `/show/sound/{path}` (behind the board gate) and from `/admin/show/sound/{path}` (behind the backoffice authentication), both served by `ShowSoundDelivery` with range processing so seeking in long tracks still works. Two routes rather than one because the two surfaces have different gates: the board cookie does not exist in the backoffice iframe, and an audio element that follows a redirect to the gate page fails silently. Latency does not suffer: the proxy runs on the origin the board is already connected to, so it saves the second DNS and TLS handshake that the blob host cost, and the blobs carry `Cache-Control: private, max-age=31536000, immutable` (every upload gets a unique name), so a sound is fetched once per device.

### Fail fast on an unknown migration state

- **The migrate step names the problem before Umbraco aborts.** `TicketingMigrationComponent` runs `MigrationStateCheck` between the forced reset and `Upgrader.ExecuteAsync`: it reads `umbracoKeyValue` at the upgrader's `StateValueKey` and accepts an empty value (fresh database or forced replay), every source state in the plan's `Transitions` and the plan's `FinalState`. Anything else is a state that only an unmerged branch knows (the dev incident above), so the component logs one error line and throws a `DomainException` with the same text: `Ticketing migration plan does not know the stored state "<state>" of database "<database>"; last known step is "<final>". Reset the state or deploy the branch that owns it.` The database name is the `Initial Catalog` of `ConnectionStrings:umbracoDbDSN` (the data source when the DSN names none). Without the check Umbraco's executor throws `InvalidOperationException: The migration plan "Ticketing" does not support migrating from state "…"` deep inside the boot, the process dies with exit code 134 and the pipeline log ends in a stack trace that names neither the database nor the last known step. The exception still leaves the process through `BootUmbracoAsync` as an unhandled exception, so the stack trace follows the line; the diagnosis is the first thing the log shows and repeats in the `Unhandled exception` header. The Show module has no plan states (`ShowSchema` is idempotent DDL with a `SchemaInfo` version row), so it needs no check. The unit test in `tests/RedAnts.Ticketing.Tests/Infrastructure` runs the real `TicketingMigrationPlan` against a fake `IKeyValueService` and pins the exact line.
- **The deploy summary shows the log tail.** Both migrate steps pipe `dotnet RedAnts.dll --migrate` through `tee migrate.log` with `set -o pipefail`; the default `bash -e` shell of a `run` step does not enable it, and without it `tee` would hide the exit code and the deploy would continue on a failed migration. A step gated on `failure() && steps.migrate.outcome == 'failure'` appends the last 40 lines of the log to `$GITHUB_STEP_SUMMARY` under the heading "Migration failed", so the diagnosis is visible on the run page without opening the step log. Recovery is unchanged: set `umbracoKeyValue` (`Umbraco.Core.Upgrader.State+Ticketing`) on that database back to the last step the deployed plan knows, or deploy the branch whose plan contains the stored state.

### Shared kernel, architecture tests and domain errors

- **`RedAnts.Kernel` carries only what every module needs.** `SwissTime`, the three exceptions, `CheckResult`, `EmailAddress` and `Money` live there because Ticketing, Show and the Host all need them and none of them may reference another module. The Kernel references no package at all; an ArchUnitNET rule keeps it that way, so nothing from Umbraco, NPoco, ASP.NET or a module can creep in through it.
- **Architecture rules are tests, not a document.** `tests/RedAnts.Architecture.Tests` loads the four assemblies once and checks the layering, the module boundaries, the handler conventions, the port rule, the infrastructure access rule and the naming rule (23 tests, none skipped). The naming rule tolerates the existing `…Service`/`…Editor`/`…Adapter`/`…Store` types through `legacy-names.txt`; the list only shrinks (a second test fails when a listed type no longer exists) so every rename removes a line and no new type can hide behind the old ones. Umbraco `Composer` classes and the `*Extensions` registrations are allowed across the Host/module boundary because `[ComposeAfter]` and `Program.cs` need the types. Every rule was proven with a deliberate violation before it was committed; ArchUnitNET keys types by full name, so two libraries must not compile a view on the same relative path (the generated `AspNetCoreGeneratedDocument` classes would collide, in the tests and in the view engine).
- **`ArticleGuid` survives a price save.** The price repositories delete and re-insert their category rows; before the fix every save generated fresh `ArticleGuid`s, which broke the link to already issued tickets. `ArticleGuids` reads the existing rows first and reuses the GUID by tier and category (event and season prices) or by id, then by label (season add-ons).
- **`EventPrice` copies must go through `With…`.** Quota, conversion-only and category edits used to rebuild the aggregate with `FromPersistence` and dropped `ConversionOnly` on the way. The `WithSalesQuota`/`WithAdmissionQuota`/`WithConversionOnly`/`WithCategories` methods validate the changed field and keep the rest, so a partial edit can no longer reset another one.
- **Domain errors end in one place.** `DomainErrorFilter` is a global MVC exception filter in the Host: `/api` and `/payrexx` callers get a 400 problem document (with the field for `ValidationException`), HTML pages get the message in `TempData["DomainError"]` and a redirect to the referring page, which `_TicketsLayout` renders as a banner. Blazor components are not MVC actions, so they catch and show the message themselves.

### Deterministic time and repository tests

- **The clock is injectable, and the injecting overloads are named `…Of`.** `AddTicketing` registers `TimeProvider.System` (through `TryAddSingleton`, so a host that already registered one keeps it) and `SwissTime` gained `TimestampOf(TimeProvider?)`, `NowOf(...)` and `TodayOf(...)` next to the `Timestamp`/`Now`/`Today` properties. The names differ from the properties because C# forbids a method and a property of the same name in one type, and renaming the properties would have touched every one of the roughly sixty call sites. The parameter is nullable and falls back to `TimeProvider.System`, which is why the sales factories (`Order.Create`, `EventTicket.Create`, `SeasonPass.Create`, `MemberCard.Create`, the bundles, visits, refunds, helpers and newsletter signups) take a trailing optional `TimeProvider? time = null`: a test pins the timestamp with `FakeTimeProvider` while production call sites stay unchanged. The timed infrastructure takes the provider by constructor instead (`DraftOrderExpiry`, whose `PeriodicTimer` runs on it, `OutboxDispatcher` for the due, backoff and purge instants, and `TicketTokenSigner` for the `iat` of a full QR token); the expiry window itself moved next to its slice as `ExpireDraftOrders.Command.Due(TimeProvider)` with the `MaxDraftAge` and `LookBack` constants. `IOrderTokens` has no expiry to make deterministic: `DataProtectionOrderTokens` protects the order id without a lifetime.
- **Repository tests run against the agent database inside a rolled-back transaction.** `tests/RedAnts.Ticketing.Tests/Database/AgentDatabaseFixture.cs` takes the DSN from the environment variable `AGENT_DSN` or the user secret `RedAnts:AgentDsn` (the test project carries the Host's `UserSecretsId`), opens one `SqlConnection` per test, starts an NPoco transaction and aborts it in `DisposeAsync`, so the tests write real rows through the real SQL and leave nothing behind. `[DatabaseFact]` sets `Skip` when no DSN is configured, which is how CI stays green without a database. The repositories reach the connection through `AgentScopeProvider`, a hand-written `IScopeProvider` whose scope hands out the fixture's database and whose `Complete`/`Dispose` do nothing (the outer transaction owns the rollback); `AgentDatabase` derives from NPoco's `Database` and implements the handful of extra `IUmbracoDatabase` members, since the interface is otherwise far too wide to fake. Gotchas: the seed ids come from `UnusedId` (a random six-digit season or event id) because the readers query the whole table and must not collide with the copied dev data; the fixture raises `Connect Timeout` to 60 seconds because `Active Directory Default` needs longer than the 15 second default when the CLI token cache is cold; and a test file that calls the database directly needs `using NPoco;` for the `params object[]` extension overloads, otherwise the compiler binds to the `CancellationToken` overload.

### Feature folders and view resolution

- **Feature folders.** Each class library holds exactly one module, so the namespaces are `RedAnts.Ticketing.*` and `RedAnts.Show.*` and the folder level `Domain/Ticketing`, `Features/Ticketing`, `Infrastructure/Ticketing` is gone. Inside `Features/` the code is cut by capability, not by technical kind: a capability folder holds its slices and ports at the root, its UI in `Admin/`, its MVC views in `Views/` and its adapters in `Infrastructure/`, so a change to one capability touches one folder and the port sits next to the slices that use it and the adapter that implements it. The former `Ports`, `*Workflow`, technical `Admin` and `Infrastructure/<Area>` folders dissolved into the capabilities (the 38 card slices by the aggregate they change, the 71 admin files by the tab they serve). The layer rule keys on the namespace segment: every namespace with an `.Infrastructure` segment is infrastructure, and a port is any interface, so ports must live directly in `RedAnts.<Module>.Features.<Capability>`. Gotcha: a capability named like a domain aggregate (`Admission`) shadows the aggregate for every type inside that namespace, because C# finds the enclosing namespace member before the using directives; the port and its adapter therefore name the aggregate `Domain.Admission.Admission`. Report DTOs stay in `Admin/` next to the component that renders them while the report port sits at the capability root, so a report reader implements a root port and returns `Admin` records.
- **View expander.** MVC views moved into the capabilities and are found by `FeatureViewLocationExpander`, registered by `AddTicketing` and `AddShow` (each module carries its own copy because the modules share no assembly that may reference ASP.NET, and each registration checks by type name that only one instance is added). `PopulateValues` stores the segment after `.Features.` of the controller namespace as `feature` (the cache key of the view engine), and `ExpandViewLocations` yields `/Features/{feature}/Views/{1}/{0}.cshtml`, `/Features/{feature}/Views/{0}.cshtml` and `/Features/Shared/Views/{0}.cshtml` before the defaults. Controllers therefore return `View("Name")`, feature views set `Layout = "_TicketsLayout"` (resolved through the expander from any capability), and only partials and layouts used across capabilities or from a Host view keep an explicit `~/Features/...` path. `/scan` is an MVC action (`ScanController` in `Admission`) instead of a Razor Page, so Razor Pages is no longer registered in `Program.cs`. Views are precompiled with their relative path as identity, so two libraries must not compile a view on the same path: the Show admin view is `Features/Admin/Views/ShowAdmin.cshtml`.
- **A zip deploy leaves removed `.cshtml` files behind, and stale views win over compiled ones.** `az webapp deploy --type zip` extracts over the existing `/home/site/wwwroot` without deleting what the new package no longer contains. After the views moved into the capabilities, the App Service still held the old `Views/Cart`, `Views/Checkout`, `Views/NextQuickBuy.cshtml`, `Views/NextEventEmbed.cshtml`, `Views/ScannerTest.cshtml`, `Views/WebTicket.cshtml`, `Views/Shared/_TicketsLayout.cshtml`, `Views/Partials/_TicketCard.cshtml`, `Features/Ticketing/` and `Pages/`; runtime compilation picked those files up, they referenced the old namespaces, and `/cart`, `/next`, `/next/embed` and `/scanner-test` answered 500 while every Umbraco template kept working. Delete the obsolete paths through the Kudu VFS API (`DELETE https://<app>.scm.azurewebsites.net/api/vfs/site/wwwroot/<path>` with `If-Match: *`, `?recursive=true` for folders, bearer token from `az account get-access-token --resource https://management.azure.com/`) and restart, or deploy with a clean target. Every environment needs this once after a view move.

### Command and read models

- **Command and read models.** Every write runs through a command slice that loads one aggregate through an `I<Aggregate>Repository` (`GetByIdAsync` / `GetByUuidAsync`, `SaveAsync`, `DeleteAsync`; the season-scoped sets `SeasonPriceTiers` and `SeasonAddOnSet` load through `LoadSeasonAsync` because the pricing commands edit the whole set), and every read runs through a query slice whose handler calls one `I…Reader` written for that screen or export and returns an immutable read-model record (`OrderListRow`, `OrderDetail`, `EventForSale`, `SeasonChoice`). A read model carries what the screen shows, never an aggregate, and lives in the capability root next to its query; exports reuse the screen queries. Components, controllers and views (the runtime-compiled Host templates included) inject handlers only; ports are used by handlers, steps and adapters. `UiRules.Ui_depends_on_handlers_only` and `PortRules.Repositories_expose_no_collections` enforce both halves; their baselines `ui-port-exceptions.txt` and `repository-collection-methods.txt` are empty and every entry needs a reason. There is no second store: readers run SQL against the same tables inside the same Umbraco scope, so a screen never shows stale data and no projection has to be rebuilt; the separation is in the code, which lets a screen query grow its own SQL (paging, search, joins across capabilities) without touching the aggregate mapping. Gotchas: a subscription is neither a command nor a query, so the Show board registers for remote commands through `ListenForShowCommands` (the handler returns the `IDisposable` registration); the development controllers (`/scanner-test`, `/dev/test-mail`) are ordinary controllers and therefore go through `GetScannerTestCards`, `SendTestMail` and `SendOrderMailSample`; a reader may depend on a repository port for a scalar lookup (`IEventConversionRuleReader.GetConversionOnlyAsync`), a component never does.

### Assessment

All eight phases of `ARCHITECTURE-PLAN.md` are live since 2026-09-10. The structure is reached and guarded by 27 architecture tests: capability folders with their own ports, views and adapters, commands that load and save one aggregate, queries that serve one screen through a read model, a user interface that depends on handlers only, a unit of work around every multi-table write, checks for the rules that need the database, and value objects for money and mail addresses.
